## Design, in brief

- **Parallel, not a replacement**, same relationship X0.1 had to the three
  existing hand-rolled approval call-sites. `app/term_provenance.py` is a
  new, independent way to get an `"active"` `VendorContractTerm` row onto
  a vendor, alongside A05's existing `resolve_case` path. Both can coexist
  on the same vendor; `resolve_vendor_term_precedence` reads whatever is
  there (regardless of which path created it) and resolves precedence.
- **`effective_from`/`effective_to` already existed** (added in A02/A05) --
  confirmed by reading `models_ledger.py` before writing any code, per the
  task's explicit instruction not to duplicate them. The only genuinely
  new column is `source_kind`.
- **Structural enforcement of "signed amendment != approved
  interpretation" is two-layered**, matching the hard rule's "never stored
  or displayed as the other":
  - *Storage*: `record_signed_amendment()` and
    `record_approved_interpretation()` are the only two functions that can
    create a non-`"contract"` term. Neither accepts `source_kind` as a
    parameter at all -- each hardcodes its own value internally. The
    former requires `document_source_ref` shaped like a real document
    citation (`ref_kind="document"` + a real `source_document_id`); the
    latter requires `case_id` to be a real, existing `Case` row. Passing
    the wrong evidence shape raises `ValueError` -- proven directly in the
    verify script (checks 6-7).
  - *Display*: `domain.term_precedence._resolution_from` is the only place
    a `TermResolution.label` is computed, and it is unconditional:
    `source_kind == "approved_interpretation"` always produces
    `INTERPRETATION_LABEL`, every other kind produces its own
    `source_kind` string as the label. There is no code path that can
    produce an interpretation result labeled as an amendment or vice
    versa.
- **"An approved interpretation applies only through a matching rule"
  reuses A05's existing mechanism, not a new one.**
  `resolve_vendor_term_precedence` only sets `interpretation_applies=True`
  when a real, `status="ACTIVE"` `PolicyVersion`'s predicates match the
  caller-supplied `CaseFacts` -- via `app.policy.find_active_matching_policy`,
  the exact function A05 already uses to decide whether a contract-term-
  conflict case can auto-resolve. This was a deliberate design choice: the
  ticket could have invented a second, parallel "does this interpretation
  apply" check, but that would risk two different definitions of "matching
  rule" drifting apart over time. Reusing the one that exists means R2's
  future "approve interpretation as reusable" decision (which will call
  `app/policy.py`'s real `approve_case_policy` to create the matching
  `PolicyVersion`) and X0.2's precedence resolution are provably talking
  about the same thing.
- **Precedence is rank-based and generic, not a hardcoded if/elif chain.**
  `_PRECEDENCE_RANK` maps each `source_kind` to a rank (signed_amendment=0,
  contract=1, approved_interpretation=2, default=3); the resolver picks the
  lowest rank among *eligible* candidates (those covering the target date,
  with interpretation additionally gated by `interpretation_applies`), and
  breaks ties within the same `source_kind` by highest `version`. This
  means a future fifth `source_kind` (if one were ever needed) is a
  one-line addition to the rank table, not a rewritten conditional chain.
- **No DB-level CHECK constraint on `source_kind`.** Every other
  enum-like string column in this schema (`Case.status`,
  `PolicyVersion.status`, `VendorContractTerm.status` itself) is validated
  by application code, not a DB constraint (confirmed by grepping the
  entire migration history -- zero `CHECK` constraints exist anywhere).
  `source_kind` follows that same precedent: `domain.term_precedence
  .resolve_term_precedence` raises `ValueError` for any candidate whose
  `source_kind` isn't one of the four recognized values (verify script
  check 15), and the two constructor functions are the only legitimate way
  to produce a non-`"contract"` row in the first place.

## Backfill: judgment call, documented (same discipline as X0.1's)

20 pre-existing `VendorContractTerm` rows in the shared dev database (and
every row any already-landed ticket's verify/dev_fixtures script creates)
backfill to `source_kind='contract'` via the migration's
`server_default='contract'` -- no per-row Python loop was needed (unlike
X0.1's `cases.subject_type` backfill, which needed one, because every
pre-X0.2 row gets the identical value). This was a deliberate choice, not
a literal reading of any spec sentence (TICKET_SPEC.md's X0.2 section
doesn't address backfill at all): `source_refs` on existing rows is
free-form locator text (e.g. `"producer_email:A05 Taco Vendor:1000bps"`),
not a structured provenance marker, so there is no reliable signal to
distinguish "this was really sourced from a signed contract" from "this
was a producer's disputed email claim" after the fact. `'contract'` is the
correct PRECEDENCE RANK for every such row to keep being read by
`app/settlement.py`'s `resolve_vendor_terms` exactly as before (it beats
default, loses to a real future signed amendment), and it is the most
honest of the four available labels for a row with no actual amendment
document or case-citation trail. Verified directly: round-tripped
`downgrade -1` / `upgrade head` twice against the live dev database; both
times all 20 rows came back `source_kind='contract'`.

## Statement labeling: how far this got wired, and what's left for R4

TICKET_SPEC.md's X0.2 "Done when" has an explicit fallback clause for this
exact situation: *"if wiring that all the way through finance_reports.py
is out of scope for a clean X0.2, at minimum show your precedence-
resolution function's own output carries the label faithfully."*

**What's done:** `domain.term_precedence.resolve_term_precedence` and
`app.term_provenance.resolve_vendor_term_precedence` both faithfully
produce `TermResolution.label == INTERPRETATION_LABEL` for any
`approved_interpretation` result, proven two ways (checks 13-14 above) --
once end-to-end through a real DB-backed vendor/case/policy fixture, once
as a pure unit check with no DB involved at all.

**What's NOT done, and why:** `services/api/app/finance_reports.py`'s
`build_statement_content` is untouched. Reading it in full before starting
this ticket (per the read-first instructions) confirmed it currently
builds a vendor statement entirely from `Settlement`/`Payout`/`Case`/
`JournalEntry` rows -- it has no notion of "which VendorContractTerm/
source_kind was used for this settlement" at all today, because A04's
`resolve_vendor_terms` (which it indirectly depends on via `Settlement`)
doesn't track that either. Wiring the label all the way into a real
statement would require: (a) `Settlement` or `SettlementLineItem`
recording which `source_kind` was actually used (a new column/field --
A04's territory, not X0.2's), and (b) the terms resolver A04/A05 actually
use for real settlement math switching from `resolve_vendor_terms`'s
plain latest-active-version lookup to `resolve_vendor_term_precedence`
(or a `case_facts`-aware variant of it). TICKET_SPEC.md's own R4 ticket
explicitly owns exactly this: *"The terms resolver reuses the pre-event
rule. The statement cites the case, the rule version and 'interpretation,
unsigned'"* -- this is R4's "settlement gate integration," not X0.2's
"data model and precedence function." Doing it here would mean
reaching into A04's settlement-calculation path and R1-R4's not-yet-built
readiness-check/gate machinery, which is explicitly out of order (X0.2
is directly before R1, not after R4). **R4 needs to: (1) call
`resolve_vendor_term_precedence` (or extend it to also return the citation
needed) from wherever it resolves a vendor's terms for a given night, (2)
carry `TermResolution.label`/`reason`/`term_id` through to
`Settlement`/the statement content dict, (3) have `build_statement_content`
surface that label verbatim.** Nothing in X0.2's code blocks that --
`resolve_vendor_term_precedence`'s signature and `TermResolution`'s fields
were deliberately kept simple and stable for exactly this future call site.

## Deviations from the plan, and why

1. **No automated unit-test files** -- standing instruction for this whole
   extension (CONTEXT.md), same as every prior ticket.
   `scripts/dev_fixtures_x02.py` / `scripts/verify_x02_term_precedence.py`
   substitute for TICKET_SPEC.md's "Done when items become automated
   tests."
2. **Backfill is a single DB-level `server_default`, not a per-row Python
   loop** -- unlike X0.1's `cases.subject_type` backfill (which needed
   per-row logic because pre-existing rows genuinely differed), every
   pre-existing `VendorContractTerm` row gets the identical
   `source_kind='contract'` value, so a plain `ADD COLUMN ... DEFAULT`
   backfills correctly in one DDL statement. Documented above and in the
   migration's own docstring, not left implicit.
3. **No DB-level CHECK constraint on `source_kind`'s four-value
   vocabulary** -- matches this schema's own established precedent (zero
   CHECK constraints anywhere in the migration history; every other
   enum-like status column is validated in application code only). See
   "Design, in brief" above.
4. **Verification is non-HTTP for this ticket** (unlike `verify_x01_*`,
   which drives real HTTP calls) -- TICKET_SPEC.md's X0.2 doesn't name a
   new endpoint, and none of its "Done when" criteria require one. Every
   check still runs against a real, migrated Postgres database and real
   SQLAlchemy sessions -- no mocks, no SQLite -- same "real DB" discipline,
   just without an HTTP hop that nothing in this ticket's scope produces.
5. **The scoped `PolicyVersion` used to prove "interpretation applies only
   through a matching rule" was constructed directly in the fixture, not
   through `app/policy.py`'s `approve_case_policy` endpoint** -- see
   "Implemented vs. incomplete" above for the full reasoning.

## Open risks

- `resolve_vendor_term_precedence` has no caller anywhere in production
  code yet (by design -- R4 is the first consumer). Until R4 wires it in,
  it is exercised only by its own verify script. This is expected for a
  ticket whose own description says "R-track has something real to call,"
  not "R-track already calls it."
- The ORM-level default (`default="contract"` on
  `VendorContractTerm.source_kind`) relies on every future `VendorContractTerm(...)`
  construction that doesn't care about provenance continuing to omit the
  field rather than passing an arbitrary string. Nothing currently
  prevents a careless future caller from passing
  `source_kind="signed_amendment"` directly to the ORM constructor instead
  of going through `record_signed_amendment` -- the structural enforcement
  described above only holds for code that calls the two sanctioned
  functions. This mirrors the same kind of trust boundary X0.1 flagged for
  its own `Approval.required_capability` (code-computed, but nothing stops
  a determined caller from constructing the ORM row directly) -- consistent
  with this codebase's general convention of enforcing invariants at the
  service-function layer, not via ORM-level validators or DB triggers.
- Terms in this codebase are append-only/versioned by convention (a
  changed mind is a new row with a new version, never an in-place edit) --
  this ticket relies on that convention continuing to hold rather than
  adding its own "don't mutate `source_kind` after creation" guard. If a
  future ticket ever starts mutating existing `VendorContractTerm` rows in
  place, this assumption would need revisiting.
- The `vendor_readiness`/`supplier_readiness` routing-table owner
  capability placeholder (X0.1's own open risk) is unchanged by this
  ticket -- still R1/R2's to resolve.
