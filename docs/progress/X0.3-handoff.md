## Design, in brief

- **`amount_cents` is written exactly once.** `propose_obligation` is the
  only function in `app/contract_obligations.py` that sets
  `ContractObligation.amount_cents`; no other function in this module (or
  anywhere else in the codebase) ever writes to that column again. This is
  the literal, structural mechanism behind TICKET_SPEC.md's "it must never
  total $40,000": not a runtime assertion recomputed on every read, but
  simply the absence of any second write path.
- **Compute-on-read, not a stored running balance -- the one explicit
  choice TICKET_SPEC.md invited this ticket to make and justify.**
  `invoiced_cents`/`paid_cents`/`credited_cents`/`remaining_cents`/
  `is_overpaid`/`overpayment_cents` are never stored as mutable columns on
  `ContractObligation`. `obligation_totals(db, obligation)` always queries
  every real `ObligationLink` row for that obligation and calls the pure
  `domain.contract_obligations.compute_obligation_totals` fresh, every
  time. I read `app/payables.py`'s `_refresh_status`/`_recompute_po`
  closely before deciding (per the task's own instruction): `SupplierInvoice`
  genuinely DOES maintain a row-locked, mutated-in-place running balance
  (`outstanding_cents`/`credited_cents`/`paid_cents`), re-derived by
  `_refresh_status` after every write. I chose the OPPOSITE approach for
  `contract_obligation`, for three reasons:
  1. TICKET_SPEC.md's own wording leans this way: "don't store these as a
     mutable running total that can drift -- compute them."
  2. The volumes are different in kind, not just degree. `SupplierInvoice`
     answers "can I pay this" under real row-lock contention, potentially
     many times across a festival's run, so caching its balance is a real
     performance/correctness need (the lock boundary IS the correctness
     boundary there). `contract_obligation`'s totals are a GROUP BY SUM over
     `obligation_links` scoped to one `obligation_id` -- a handful of rows
     per obligation in every scenario this ticket or the seed data ever
     produces. There is no realistic volume here where a cached column
     would pay for the drift risk it introduces.
  3. It makes the required property true BY CONSTRUCTION, not by careful
     bookkeeping. "Linking a PO or invoice never changes total commitment"
     cannot have a bug in a running-total UPDATE statement, because there
     is no running-total UPDATE statement -- `amount_cents` is read, never
     written a second time, full stop.

  The one place this ticket still takes a row lock despite never writing
  `amount_cents` is `link_obligation`, which locks the PARENT
  `ContractObligation` row (`_lock_obligation`, `SELECT ... FOR UPDATE`)
  for the duration of inserting a new link and recomputing totals. This
  is NOT protecting `amount_cents` (nothing writes it); it is
  SERIALIZING two concurrent "insert a link, then decide if this is now
  overpaid" calls on the SAME obligation, the same purpose `app/
  payables.py`'s `_recompute_po` locking the PO row serves for its own
  PO-excess attribution -- the thing being protected is "did we see every
  other link that already happened before deciding overpaid," not "is this
  one column safe to write."

- **Explicit, server-enforced state machine, not an if/elif chain.**
  `domain.contract_obligations.ALLOWED_TRANSITIONS` is a plain
  `dict[str, frozenset[str]]` -- `{"proposed": {"approved", "cancelled"},
  "approved": {"committed", "cancelled"}, "committed": {"invoiced",
  "cancelled"}, "invoiced": {"paid", "cancelled"}, "paid": set(),
  "cancelled": set()}`. `validate_transition(current, new)` raises
  `IllegalTransitionError` for anything not an exact entry in this table --
  an unrecognized status on either side, a same-state no-op, a skip-ahead
  (`proposed -> paid`), or a backward move after payment (`paid ->
  approved`), all rejected identically. `app/contract_obligations.py`'s
  `transition_obligation` is the ONLY function that writes
  `ContractObligation.status`, and it always calls `validate_transition`
  first, inside the same row lock used for `link_obligation`.
- **Judgment call: "cancelled" is reachable from every non-terminal state,
  not only from "invoiced."** TICKET_SPEC.md's literal arrow notation is
  "proposed -> approved -> committed -> invoiced -> paid | cancelled,"
  which read with full literalness would make an obligation uncancellable
  while merely proposed/approved/committed. That does not match how a real
  deposit/milestone/final commitment would actually be managed -- a deal
  can fall through before any invoice exists, and that must be recordable.
  `ALLOWED_TRANSITIONS` instead lets "cancelled" be reached from
  proposed/approved/committed/invoiced, never from "paid" (money has
  already been simulated as moved -- cancelling would misrepresent what
  happened, the same principle CONTRACTS.md's C04 applies to `Payout`:
  "state stays whatever the rail actually reported ... NEVER forced to
  CANCELLED once money has moved"). "paid" is reachable only from
  "invoiced," matching the spec's literal arrow exactly. Documented here,
  in the module's own docstring, and in PROGRESS.md's Deviations log.
- **`remaining_cents` deliberately ignores `invoiced_cents`, matching
  TICKET_SPEC.md's own formula.** The spec's exact words: "remaining =
  amount - paid - credited" -- not "amount - invoiced." So an obligation
  can be heavily over-invoiced (the property-supplier fixture invoices
  $12,000 against a $10,000 commitment) without that alone ever counting
  as overpaid or moving `remaining_cents` by one cent; only `payment`/
  `credit_note` links do. `is_overpaid` is defined symmetrically: exactly
  `paid_cents + credited_cents > amount_cents` (i.e. "remaining would go
  negative"), never folding `invoiced_cents` into that comparison either.
- **Overpayment opens at most one Case per obligation, ever (dedup
  check, not a fresh case per overpaying link).**
  `_open_overpayment_case_if_absent` first queries for an existing OPEN
  `Case` with `subject_type="contract_obligation"`, `subject_id=<this
  obligation>`, `reason_code="obligation_overpaid"` -- if one exists, it
  returns `None` and opens nothing new, even though the obligation is
  (still, or more) overpaid. Proven directly in the property-supplier
  fixture: the SECOND payment link (pushing paid past amount_cents) opens
  a real case; the THIRD payment link (still overpaid, by more) does not
  open a second one.
- **`route_case` is actually called from a real case-opening site for the
  first time.** X0.1's handoff noted `route_case`/`known_routes` existed
  but no production case-opening call site used them yet (A03/A05/A08's
  own case-opening is older code, untouched, and tags `subject_type`
  directly without consulting the routing table). `_open_overpayment_case_if_absent`
  calls `domain.case_routing.route_case("contract_obligation",
  "obligation_overpaid")` to resolve `Case.required_capability` -- the
  first real wiring of that function into a live code path.

## Why no new HTTP endpoint this ticket

TICKET_SPEC.md's "API additions" list (shared across the whole prevention
extension) does not name an obligations/links endpoint for X0.3
specifically -- the endpoints it does list (`GET /readiness`, `GET
/payables/invoices`, `GET /forecast`, etc.) all belong to R/F/S-track
tickets that come later and haven't started. X0.2 made the identical call
for the identical reason (its own handoff: "TICKET_SPEC.md's X0.2 section
doesn't ask for one") and that precedent held up through regression --
nothing in X0.1/X0.2 needed HTTP access to X0.2's new column before R4
exists to consume it. The same reasoning applies here: R1/F1/S1 (the next
tickets that will actually create/read/link real obligations from a UI or
agent) are the natural first callers of a real endpoint, and they haven't
been designed yet. Building a guessed endpoint shape now risks the same
kind of premature commitment TICKET_SPEC.md's own "agents propose, code
decides" discipline warns against for business logic -- it applies just as
well to API surface. Every acceptance criterion below is independently
verified through direct, real-database Python calls (the same "real DB,
hand-checked fixture" discipline X0.2 established), not description.

## Deviations from the plan, and why

1. **No automated unit-test files** -- standing instruction for this whole
   extension (CONTEXT.md), same as every prior ticket.
   `scripts/dev_fixtures_x03.py` / `scripts/verify_x03_obligations.py`
   substitute for TICKET_SPEC.md's "Done when items become automated
   tests."
2. **Compute-on-read instead of a stored running balance** -- the one
   explicit choice TICKET_SPEC.md invited; see "Design, in brief" above
   for the full three-part reasoning (spec's own wording, volume/
   contention difference from `SupplierInvoice`, and "true by
   construction" for the required property).
3. **"Cancelled" is reachable from proposed/approved/committed, not only
   from "invoiced"** -- a judgment call on TICKET_SPEC.md's literal arrow
   notation; see "Design, in brief" above and the module's own docstring
   for the full reasoning (a deal falling through before any invoice
   exists must be recordable; "paid" stays the only truly un-cancellable
   terminal state, matching C04's Payout precedent of never un-doing a
   state once real money has moved).
4. **A new `subject_type`, `"contract_obligation"`, added to
   `domain.case_routing.SUBJECT_TYPES`** -- not one of X0.1's original
   five, added because none of those five honestly describes "a case
   about one specific over-linked obligation row." Documented inline in
   `case_routing.py`, in this handoff, and in PROGRESS.md's Deviations
   log, per the task's explicit instruction not to silently invent one.
5. **No new HTTP endpoint** -- see the dedicated section above. Same
   deviation shape as X0.2's own "verification is non-HTTP," for the same
   underlying reason (nothing in this ticket's own "Done when" requires
   one, and the real future caller -- R1/F1/S1 -- hasn't been designed
   yet).
6. **No new capability constants** -- TICKET_SPEC.md's X0.3 section names
   none (unlike X0.1's five explicitly-named ones); this ticket reuses
   `finance_lead` and `manage_payables`. See "Capabilities reused, not
   added" above for the exact mapping and reasoning.
7. **`contract_totals` (aggregating across every obligation sharing a
   `contract_id`) was added beyond the literal per-row schema
   TICKET_SPEC.md's X0.3 bullet list describes** -- the flagship "Done
   when" scenario ("a $20,000 contract ... shows commitment $20,000")
   only makes sense read at the CONTRACT level when a $20,000 contract is
   actually split into a $5,000 deposit obligation and a $15,000 final
   obligation (two rows, one per `kind`, which is how `kind`'s own
   enum -- "deposit | milestone | final" -- is clearly meant to be used,
   one value per row, not a single row representing a combined payment
   plan). `contract_totals` is the aggregation this reading requires; it
   is additive (a new function, not a changed table shape) and documented
   fully in "Design, in brief" above, including the judgment call to
   EXCLUDE cancelled obligations from the aggregate (a cancelled
   commitment is no longer a real one).

## Open risks

- `counterparty_id` (vendor or supplier id, depending on
  `counterparty_type`) and `obligation_links.subject_id` (po/invoice/
  payment/credit_note id, depending on `subject_type`) are both loose
  string references, not foreign keys -- same trust boundary X0.1 flagged
  for `Case.subject_type`/`subject_id` and `Approval.subject_type`/
  `subject_id`: nothing at the DB layer stops a future caller from writing
  a `subject_id` that doesn't actually exist in the table its
  `subject_type` implies. Validated only in `app/contract_obligations.py`'s
  own write paths (which don't currently look up the referenced row to
  confirm it exists, either -- they trust the caller). A future ticket
  wiring a real endpoint on top of this should add that existence check
  at the endpoint/service boundary before trusting user input.
- `contract_id`'s "should be a `source_documents.id` with
  `document_kind='CONTRACT'`" convention is enforced nowhere -- any real
  `source_documents.id` satisfies the FK. See "Implemented vs. incomplete"
  above.
- The overpayment dedup check looks for an OPEN case with the exact
  `reason_code="obligation_overpaid"` -- if a future ticket's workflow
  ever RESOLVES that case while the obligation is STILL overpaid (e.g. a
  human marks it resolved without actually fixing the underlying
  over-linking), the next overpaying link will open a brand new case
  rather than recognizing the condition persists. This mirrors exactly
  how `app/payables.py`'s own `INVOICE_EXCEEDS_PO` case handles the
  analogous situation (resolved only when the condition's root cause is
  actually gone) -- consistent with existing precedent, not a new gap.
- `link_obligation`'s row lock on the PARENT obligation serializes
  concurrent links on the SAME obligation, but does nothing to prevent
  (nor need to prevent) concurrent links on DIFFERENT obligations that
  happen to reference the SAME underlying PO/invoice/payment/credit_note
  row from different obligations simultaneously -- that is a legitimate
  scenario this ticket allows (a single invoice split across two
  obligations), not a bug, but worth knowing before a future ticket adds
  any cross-obligation "total linked amount must not exceed the subject's
  own amount" invariant (TICKET_SPEC.md does not ask for one; S-track's
  own invoice-matching engine, S2, is the ticket that actually reasons
  about an invoice's OWN billable/authorized amounts).
