## Design, in brief

- **Parallel, not a replacement.** The three existing hand-rolled
  approval call-sites CONTEXT.md names (A05's `Case.resolution_*`/
  `resolved_by`, A08's `SupplierInvoice.variance_approved_by/at`, A07/A08's
  `SupplierPayment.approved_by/approved_capability`) are untouched --
  verified by re-running their own verification scripts (below). The new
  `Approval` table is a second, generic mechanism for subject types that
  don't have a hand-rolled home yet (`vendor_readiness`,
  `supplier_readiness`, `forecast_snapshot`, and S4's new invoice-exception/
  payment-release decisions on `supplier_invoice`).
- **`subject_type`/`subject_id` is a loose string pair, not a foreign
  key.** Deliberately: X0.1's own "Done when" requires a case to carry
  `subject_type="forecast_snapshot"` pointing at an id string before F1
  creates that table at all. Proven directly: a fixture-only `Case` row
  with `subject_id="fcst-not-yet-real-<run>"` round-trips through
  `GET /cases/{id}` with no FK violation, no forecast_snapshot table
  existing anywhere in the schema. **F1 should feel free to add a real FK
  for forecast_snapshot specifically once that table exists -- nothing here
  blocks that, and a later FK addition doesn't undo anything here.**
- **The approval endpoint's capability check is dynamic, not static.**
  Every other capability-gated endpoint in this codebase does
  `Depends(require_capability(SOME_CONSTANT))` -- a capability baked in at
  route-registration time. `POST /approvals`'s required capability depends
  on the request body's `action` field, which `require_capability`'s
  factory shape can't express. The endpoint instead authenticates via
  `get_current_user` (401 first, same as everywhere else) and then calls
  the exact same `get_user_capability_codes()` primitive
  `require_capability` is built from, with a capability resolved from
  `domain.approvals.required_capability_for_action(action)` at request
  time. This is the same re-read-from-DB-every-request guarantee, not a
  parallel/weaker check -- proven by the capability-check tests below.
- **The stored `required_capability`/`actor_capability` are code-computed,
  never client-supplied.** The request body has no capability field at
  all; `record_approval()` re-derives the required capability itself
  rather than trusting whatever the router computed, so a caller can never
  cause a broader capability than the action actually needed to be
  recorded as having been exercised.
- **Routing table is pure code, not a DB table.** TICKET_SPEC.md asks for
  a "routing table," not a `routing_table` schema -- implemented as a
  plain Python dict in `domain.case_routing` (same convention as
  `domain.policy`'s pure, DB-free deterministic checks), so it's reviewable
  in a diff and requires no migration to extend.

## Backfill: exactly how existing rows were labeled (judgment call, documented)

TICKET_SPEC.md's literal text says "Backfill existing rows as
`vendor_run`." Reading the actual `cases` table before writing the
migration showed two genuinely different shapes of existing row:

1. A05's `vendor_contract_term_conflict` cases: always carry a real
   `vendor_id`. These are exactly what "vendor_run" describes -- backfilled
   as `subject_type="vendor_run", subject_id=<vendor_id>`.
2. A08's `DUPLICATE_SUPPLIER_INVOICE`/`POSSIBLE_DUPLICATE_SUPPLIER_INVOICE`/
   `INVOICE_EXCEEDS_PO` cases: always carry `vendor_id=None` and an
   `evidence_refs` entry shaped `{"ref_kind": "supplier_invoice", "ref_id":
   <id>, "role": "subject"}` (literally what `app/payables.py`'s
   `_open_case` has always written). These are not about a vendor's night
   at all -- backfilled as `subject_type="supplier_invoice", subject_id=
   <that invoice id>`, extracted from `evidence_refs` by the migration.
3. A03's reconciliation cases found mid-ticket (see Deviations): always
   carry `vendor_id` except for two festival-level bank-deposit reason
   codes (`deposit_settlement_overdue`, `bank_deposit_variance_unexplained`)
   which have `vendor_id=None` and no invoice evidence_refs either --
   backfilled as `subject_type="vendor_run", subject_id=<the case's own
   id>` (the migration's documented fallback for "matches neither pattern").

This was a deliberate judgment call, not a literal word-for-word
application of the spec sentence, made because applying `vendor_run` to
every row regardless of content would have mislabeled every A08 invoice
case as being about a vendor's settlement run, which it demonstrably is
not (no `vendor_id`, a real invoice reference instead). The verification
script (`verify_x01_cases_approvals.py` check 1) confirms the result:
every pre-existing row ends up correctly and non-nullly tagged.

append-only), 5 new capabilities, the routing table, the generic approval

## Deviations from the plan, and why

1. **A fourth existing case-opening call site was found and patched.**
   CONTEXT.md names three hand-rolled *approval* call-sites (A05, A08's
   `SupplierInvoice`, A07/A08's `SupplierPayment`/`Payout`), but a fourth,
   separate *case-opening* call site exists in
   `services/api/app/reconciliation.py` (A03) that wasn't mentioned
   anywhere in the ticket's read-first list. It uses the exact same `Case`
   table (not a parallel approval mechanism -- A03's cases are resolved
   through A05's same `resolve_case`/`approve_case_policy` endpoints), so
   it was in-scope to tag the same way as the other two case-opening sites
   (policy.py, payables.py). Patched additively (two new kwargs on an
   existing `Case(...)` call), verified via the full fresh-database run
   above (A03's own 32/32 checks still pass).
2. **Two pre-existing raw-test-fixture `Case` rows, in OTHER tickets' own
   already-landed verify/dev_fixtures scripts, are NOT tagged and were
   deliberately left alone.** `scripts/verify_a07_payouts.py` and
   `scripts/dev_fixtures_a08.py` each construct one bare `Case(...)` row
   directly (test-only blocking scaffolding, not through any production
   code path) with reason codes `a07-verify-hold-*` / `A08_VERIFY_HOLD`.
   Editing other tickets' own test scripts was judged out of scope and
   unnecessary risk for zero required benefit; `verify_x01_cases_approvals.py`
   names these two exact reason codes as a documented, known exception
   rather than silently ignoring unexpected nulls.
3. **The shared dev `encore` database accumulated a handful of stale,
   unbackfilled `Case` rows mid-session**, created by my own intermediate
   testing in the brief window between "the migration's one-time backfill
   ran" and "`reconciliation.py`'s ongoing tagging was patched" (deviation
   #1 above). These were filled in afterward with the exact same backfill
   logic the migration itself uses (an `UPDATE` of the two new nullable
   columns on existing rows -- not a deletion, not a change to any other
   column). Flagged here for transparency even though it's a session
   artifact, not a code defect (the from-scratch database run proves the
   code itself produces zero such rows).
4. **No automated unit-test files** -- standing instruction for this whole
   extension (CONTEXT.md). `scripts/dev_fixtures_x01.py` /
   `scripts/verify_x01_cases_approvals.py` substitute for TICKET_SPEC.md's
   "Done when items become automated tests," same convention as every
   prior ticket.
5. **Backfill labeling was a judgment call, not literal spec text** -- see
   the dedicated section above. Documented per the task's explicit

## Open risks

- The `vendor_readiness`/`supplier_readiness` routing-table owner
  (`finance_lead`/`manage_payables`) is a placeholder judgment call, not a
  capability the spec names explicitly for that case_kind. R1/R2 may want
  to introduce a dedicated capability instead of reusing these.
- The generic `Approval` table has no concept yet of "pending" vs.
  "decided" -- every row represents an already-granted decision (consistent
  with how every other approval-shaped thing in this codebase works:
  `PolicyVersion`, `SupplierPayment`, etc. are created already-approved,
  never as a separate mutable request row). If R2/S4/F5 need an actual
  multi-step request/grant workflow instead of "record the decision that
  was already made," that's new modeling on top of this table, not a
  change to it.
- `Approval.case_id` is nullable and only loosely validated (must match
  the case's subject_type/subject_id if given) -- there is no requirement
  that a `release_supplier_payment` approval cite any case at all. S4 will
  need to decide whether its real release step always requires a prior
  exception-case reference or not.
