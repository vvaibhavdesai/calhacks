## Authentication / session mechanism

Server-issued JWT (HS256, symmetric secret `AUTH_JWT_SECRET`), no third-party
OAuth provider. Rationale:

- AGENT_HANDOFF.md: "one initial user may hold all roles" for v1, and no
  requirement for external identity federation. A third-party OAuth
  dependency would add setup friction (and an external account/credential)
  that the current product scope does not need.
- C00 leaves "auth/session mechanism chosen" as a setup choice, not a
  reopened product decision.

Mechanics, implemented in `services/api/app/auth.py`:

- Passwords hashed with `bcrypt`; plaintext is never stored, logged, or
  echoed back.
- A JWT carries only `sub` (user id), `iat`, `exp` -- **never** a capability
  list. Every capability check (`require_capability(code)` in `app/auth.py`)
  re-reads `user_capabilities` from PostgreSQL for the current request. This
  is the concrete mechanism behind "no browser role-switch bypass": even a
  token forged with the correct secret but a smuggled `"capabilities"` claim
  is ignored server-side (covered by
  `test_browser_cannot_role_switch_by_forging_token_claims` in
  `services/api/tests/test_auth.py`).
- `GET /health/*` is intentionally unauthenticated (orchestrators must be
  able to probe liveness without credentials); every other mutating route
  added so far (`POST /api/v1/example/protected-write`) requires both
  authentication (401 if missing/invalid) and a specific capability (403 if
  authenticated but unauthorized). Real business write endpoints in A02+
  must reuse `require_capability`, not invent a parallel check.
- `AUTH_JWT_SECRET` has no default; `Settings` (pydantic-settings) raises a
  validation error at process startup if it (or `DATABASE_URL`) is absent,
  so a misconfigured deployment fails loudly at boot, not with a silent
  unauthenticated/insecure default.

The proposed C00 names `AUTH_ISSUER` / `AUTH_AUDIENCE` (implying a federated
OIDC-style issuer/audience model) are not used: they don't apply to a
self-issued symmetric JWT with one logical audience. If a later task adds a
real OAuth/OIDC provider, that is a breaking C00 change requiring its own
ADR, not a silent reinterpretation of these fields.

## Document storage

Pluggable interface (`services/api/app/storage/base.py`,
`DocumentStorage.save/read/exists`) with exactly one implementation for A01:
`LocalFilesystemStorage` (`services/api/app/storage/local_fs.py`), writing
under `DOCUMENT_STORAGE_ROOT` (default `./.data/documents`, override via env;
containers use a named volume mounted at `/data/documents`). Keys are
resolved and checked against path traversal (`..`, absolute paths) before
any filesystem access.

A real object-store backend (S3-compatible, etc.) is a later swap behind the
same `DocumentStorage` interface -- callers must depend on the abstract
interface, never import `LocalFilesystemStorage` directly outside
`get_document_storage()`. This is intentionally not redesigned later, only
extended with a second implementation selected by
`DOCUMENT_STORAGE_BACKEND`.

## Secret injection / environment variables

Every required configuration name used by A01 is listed in `.env.example`
(repo root) and `apps/web/.env.example`. Summary:

- `DATABASE_URL`, `AUTH_JWT_SECRET` -- required, no default, fail startup if
  missing.
- `AUTH_TOKEN_TTL_MINUTES`, `DOCUMENT_STORAGE_BACKEND`,
  `DOCUMENT_STORAGE_ROOT`, `ALLOWED_ORIGINS`, `APP_ENV` -- optional, sensible
  dev defaults.
- `ADMIN_EMAIL`, `ADMIN_INITIAL_PASSWORD` -- consumed only by
  `scripts/seed_admin.py`, never read by the running API/worker process.
- `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` -- present in `.env.example` for
  forward compatibility with C00's proposed variable list, but **not read by
  any code path in A01**. `ANTHROPIC_MODEL` is set to the literal string
  `TBD-pending-user-authorization` in `.env.example` and must stay that way
  until the user explicitly authorizes a specific model/spend in A06.
  **2026-10-24 update:** the user has pre-selected `claude-sonnet-5` as the
  model to record once A06 is actually started, but has NOT yet provided an
  `ANTHROPIC_API_KEY` and explicitly chose to defer A06 (live Claude/LangGraph
  execution) until credentials are available, continuing with A07+ in the
  meantime. Do not set `ANTHROPIC_MODEL` to a real value or make any live
  call anywhere in the codebase until A06 is actually picked up with a key in
  hand -- this line records the decision, it is not itself an authorization
  to start A06.
- The frontend (`apps/web`) receives exactly one env var,
  `VITE_API_BASE_URL`, which is a public origin, not a secret. No database
  URL, JWT secret, or Anthropic key is ever referenced from `apps/web`.

Secret injection for a real deployment (staging/production) is explicitly
out of scope for A01 and belongs to A10; locally, `.env` (gitignored) feeds
`infra/docker-compose.yml` via Compose's `${VAR}` interpolation.
